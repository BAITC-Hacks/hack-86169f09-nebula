# EventMatch AI

Рабочий репозиторий команды Nebula для трека 06 HackAlem AI: «Умный подбор подрядчиков».

## Сервер в ветке backend

Добавлен FastAPI-бэкенд и подключение существующего сайта к серверному поиску.
После установки `python -m pip install -r requirements.txt` запустите `python run.py`.
Сайт: http://127.0.0.1:8001/, проверка API: http://127.0.0.1:8001/docs.
Полная инструкция, схема API, алгоритм, тесты и ограничения: [BACKEND.md](BACKEND.md).

Стартовый набор содержит **16 синтетических профилей**; полный каталог организаторов
нужно подключить отдельно. По умолчанию объяснения шаблонные; предусмотрен опциональный
AI-шлюз с проверкой выбранных фактов. Ниже сохранён исходный план команды; его отметки
отражают предыдущий checkpoint, а актуальные возможности сервера описаны в BACKEND.md.

## Простая идея

Пользователь выбирает город, дату, формат мероприятия, категорию подрядчика и бюджет.

Сервис показывает до трёх подходящих подрядчиков из выданного каталога и объясняет каждый выбор конкретными фактами:

- подрядчик работает в нужном городе;
- берёт нужный формат мероприятия;
- свободен в выбранную дату;
- его цена «от» укладывается в бюджет;
- при запросе проверяются язык и длительность.

Если подходящих нет, сервис объясняет причину: такой категории нет в городе или кандидаты не проходят условия.

## Границы задачи

В проект не входят бронирование, заявки подрядчикам, платежи и уведомления.

Цена в каталоге является ценой «от». Сервис не обещает окончательную стоимость услуги.

Данные каталога анонимизированы. Поля `synthetic`, `city_imputed` и `price_imputed` должны быть видны в карточке, когда они равны `true`.

## Роли команды

### Участник 1 — данные и алгоритм

- Добавляет исходный CSV в `data/`.
- Создаёт загрузчик и проверку структуры данных.
- Реализует фильтры: город, категория, формат, бюджет, дата, язык и длительность.
- Создаёт детерминированное ранжирование и объяснение причин пустой выдачи.
- Готовит тестовые сценарии из ТЗ.

### Участник 2 — сервер и AI

- Создаёт API поиска и структуру ответа.
- Добавляет AI-объяснение только по отобранным профилям.
- Проверяет факты в объяснении: цена, язык, формат, дата и доступность.
- Делает запасной шаблон объяснения, чтобы сервис работал без API-ключа.
- Не передаёт в модель данные, которых нет в каталоге.

### Участник 3 — интерфейс и демо

- Создаёт форму поиска и карточки результата.
- Показывает три понятных состояния: «подобрали», «такой категории в городе нет», «кандидаты есть, но условия не пройдены».
- Отображает причины исключения и метки качества данных.
- Готовит короткое живое демо и скриншоты для README.

### Этап 1. Данные и базовый поиск

Цель: по форме получить корректный список доступных кандидатов.

- [ ] Скачать и добавить исходный CSV как `data/contractors.csv`.
- [x] Добавить браузерный checkpoint: проверка 13 обязательных колонок перед подключением CSV.
- [ ] Проверить 13 колонок: ID, имя, категории, город, цена, форматы, языки, длительность, занятые даты, описание и флаги.
- [ ] Реализовать строгие фильтры.
- [ ] Исключить занятого подрядчика до ранжирования.
- [ ] Вернуть не более трёх кандидатов.
- [ ] Зафиксировать одинаковый порядок для одинакового запроса.

Готово, когда один и тот же запрос дважды возвращает одни и те же карточки в том же порядке.

### Этап 2. Объяснимый подбор

Цель: у каждой карточки есть собственное объяснение, основанное на каталоге.

- [ ] Ввести понятный расчёт ранга: обязательные условия + число дополнительных совпадений.
- [ ] Сформировать для каждой карточки 1–2 конкретных предложения.
- [ ] Упомянуть только подтверждённые поля профиля.
- [ ] Объяснить, почему кандидатов меньше трёх.
- [ ] Считать исключения по причинам: нет формата, выше бюджета, занят, нет языка, недостаточная длительность.

Пример хорошего объяснения: «Свободен 15 октября, ведёт корпоративы, говорит на русском и английском; цена от 1 000 000 ₸ укладывается в ваш бюджет».

### Этап 3. AI-функция

Цель: AI делает объяснение полезнее, но не подменяет правила отбора.

- [ ] Передать в модель только выбранные данные карточки и запрос пользователя.
- [ ] Запросить структурированный ответ: 1–2 предложения с причинами выбора.
- [ ] Проверить ответ модели и заменить его шаблоном при ошибке или неподтверждённом факте.
- [ ] Показывать, что решение получено из каталога и правил.
- [ ] Хранить API-ключ только в `.env`, не коммитить его.

### Этап 4. Интерфейс

Цель: жюри может самостоятельно выполнить поиск без помощи разработчика.

- [ ] Сделать форму с обязательными полями и понятной валидацией.
- [ ] Показать максимум три карточки.
- [ ] Показать «от» перед ценой.
- [ ] Выделить занятость как причину исключения.
- [ ] Добавить метки synthetic / восстановленный город / восстановленная цена.
- [ ] Сделать ссылку или кнопку для загрузки трёх демо-запросов.

### Этап 5. Обязательные демонстрации

- [ ] Плотная категория: Алматы, ведущий, корпоратив, 15.10.2026, бюджет 2 000 000 ₸.
- [ ] Тот же запрос на 25.12.2026: выдача должна измениться из-за занятости.
- [ ] Редкая категория: Алматы, флорист, свадьба, 15.10.2026, бюджет 1 000 000 ₸.
- [ ] В городе нет категории: Астана, декоратор.
- [ ] Кандидат есть, но не проходит условия: Астана, флорист, свадьба, 15.10.2026, бюджет 1 000 000 ₸.
- [ ] Запустить одинаковый запрос дважды и показать одинаковый порядок.

## Предлагаемая архитектура

```text
Форма поиска
      ↓
API поиска
      ↓
Проверка условий → причины исключения
      ↓
Детерминированное ранжирование
      ↓
AI-объяснение с проверкой фактов
      ↓
До 3 карточек или понятный пустой результат
```

## Технологии

Предпочтительный старт:

- Python + FastAPI для сервера;
- CSV как единственный источник данных;
- HTML/CSS/JavaScript для интерфейса;
- OpenAI API или NVIDIA API только для объяснений;
- шаблонный режим при отсутствии API.
